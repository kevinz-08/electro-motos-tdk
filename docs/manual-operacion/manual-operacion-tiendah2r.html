1. Resumen: cómo funciona la tienda

tiendah2r no es un solo programa en un solo lugar: son cuatro servicios en la nube que trabajan juntos. Si uno deja de funcionar (por ejemplo, por un pago pendiente), la tienda pierde esa parte aunque los otros tres sigan activos.

2. Google Cloud Platform (GCP)

Consola: https://console.cloud.google.com · Facturación: menú ☰ → Facturación

Para qué sirve

  • Cloud Run ejecuta la API de la tienda (servicio electro-motos-api): crea pedidos, confirma pagos (Wompi / Mercado Pago), descuenta stock, envía correos de confirmación y se conecta con Vendelo para los envíos.
  • Login con Google: el proyecto de GCP aloja las credenciales OAuth (Cliente ID y secreto) que permiten a los clientes entrar con su cuenta de Google.
  • Secret Manager guarda las claves secretas de la API (base de datos, JWT, pasarelas de pago).
  • Artifact Registry guarda las imágenes (versiones) de la API que se despliegan.

Qué pasa si se suspende

Los clientes pueden ver el catálogo, pero no pueden comprar, iniciar sesión ni ver pedidos; los pagos aprobados no se confirmarían y los correos no saldrían. Es el servicio más crítico para vender.

Facturación

  • Corte: el día 1 de cada mes.
  • Cloud Run cobra por uso (peticiones y tiempo de cómputo) y tiene una cuota mensual gratuita; con el tráfico actual el costo suele ser bajo, pero un pico de visitas o un error puede subirlo.
  • Se paga con la tarjeta/método registrado en la cuenta de facturación de GCP. Si el cobro falla, Google avisa por correo y puede suspender los servicios.

Qué revisar (mensualmente)

  1. Facturación → Informes: ver el gasto del mes en curso y compararlo con el anterior.
  2. Facturación → Presupuestos y alertas: confirmar que existe una alerta de presupuesto y que llega a un correo que se revise.
  3. Facturación → Administración de pagos: tarjeta vigente y sin vencer.
  4. Cloud Run → servicio electro-motos-api → pestaña Registros (logs): buscar errores repetidos.
  5. Comprobar que la API responde: abrir [URL de la API]/health (debe responder "ok").

Problemas típicos

SíntomaQué revisar

3. Vercel

Consola: https://vercel.com/dashboard

Para qué sirve

  • Aloja y publica el frontend (aplicación Next.js): home, catálogo, fichas de producto, carrito, checkout, panel de administración y páginas de SEO.
  • Cada vez que se sube código nuevo al repositorio de GitHub, Vercel construye y publica la nueva versión (deploy).
  • Guarda las variables de entorno de la web (conexión a la base de datos, claves de NextAuth, Cloudinary, etc.).
  • Gestiona el dominio www.tiendah2r.com y su certificado HTTPS.

Qué pasa si se suspende

La tienda deja de abrir por completo: ni catálogo, ni carrito, ni panel de administración.

Qué tener en cuenta

  • Plan: verificar en Settings → Billing qué plan está activo (Hobby o Pro). Los términos de Vercel indican que el plan Hobby es para uso personal/no comercial; una tienda con ventas suele requerir Pro. Confirmar con el plan actual y las condiciones vigentes.
  • Fecha de cobro: si el plan es de pago, Vercel cobra según la fecha de alta de la suscripción (no necesariamente el día 1). Anotar aquí la fecha real: [completar con el ciclo de facturación que muestre la cuenta].
  • Límites: Vercel mide ancho de banda, invocaciones de funciones y minutos de build. Revisar Usage de forma mensual.
  • Almacenamiento de despliegues: cada rama o deploy ocupa espacio. Por eso el proyecto evita publicar ramas innecesarias.
  • Dominio: la renovación del dominio se paga donde se compró (registrador), no en Vercel, salvo que se haya comprado allí. Verificar el vencimiento.

Qué revisar (mensualmente)

  1. Dashboard → proyecto → Deployments: el último deploy de Production debe estar en estado Ready.
  2. Settings → Billing / Usage: consumo y próxima factura.
  3. Settings → Domains: dominio con estado válido y sin advertencias.
  4. Pestaña Logs: errores recurrentes de las funciones del servidor.

Problemas típicos

SíntomaQué hacer
La web no abreRevisar estado de la cuenta y del último deploy; probar el enlace *.vercel.app del proyecto.
Un deploy fallóDeployments → abrir el deploy fallido → ver el log. Se puede volver a la versión anterior con Promote / Rollback sobre un deploy que estaba bien.
Cambié algo en el admin y no se veEn /admin/configuracion usar "Refrescar tienda" (invalida la caché).
No tocar las variables de entorno sin avisar al desarrollador: varias deben ser idénticas a las de la API en GCP (por ejemplo INTERNAL_API_SECRET). Un valor distinto rompe el login.

4. Neon (base de datos)

Consola: https://console.neon.tech

Para qué sirve

  • Es la base de datos PostgreSQL donde viven: productos, categorías, stock, precios, usuarios, pedidos, pagos, banners, reseñas y la cola de correos.
  • Tanto la web (Vercel) como la API (GCP) se conectan a ella mediante la variable DATABASE_URL.
  • Es "serverless": el cómputo se apaga tras unos minutos sin consultas y se enciende al recibir una.

Qué pasa si se suspende o se agota

Sin base de datos no hay catálogo ni pedidos. Ya ocurrió una vez (octubre de 2026): se agotó la cuota de cómputo del mes y la tienda mostró el error "exceeded the quota". Por eso el proyecto fue optimizado para consultar la base lo mínimo posible.

Facturación

  • Corte: el día 1 de cada mes.
  • Neon cobra por CU-hours (tiempo de cómputo encendido × tamaño del cómputo) y por almacenamiento, no por número de consultas.
  • Cada plan incluye una cantidad de CU-hours al mes; superarla bloquea el servicio (plan gratuito) o genera cobros adicionales (planes de pago). Confirmar el plan vigente en Billing.

Qué revisar (mensualmente, y a mitad de mes)

  1. Billing → Usage: CU-hours consumidas vs. incluidas. Meta del proyecto: no superar ~2 CU-hours por día.
  2. Monitoring → Compute: el cómputo debe estar apagado la mayor parte del día, con picos cortos al comprar o usar el admin.
  3. Configuración de Autoscaling: mínimo y máximo 0,25 CU, y Scale to zero activado.
  4. Tarjeta vigente en Billing.
  5. Almacenamiento usado (Storage) y que existan copias de seguridad / restore window según el plan.

Qué sube el consumo (y conviene evitar)

  • Dejar el panel /admin abierto navegando de forma constante.
  • Scripts masivos o herramientas (Prisma Studio, cargas de catálogo) que mantienen la conexión abierta.
  • Tráfico automatizado o bots sobre rutas dinámicas (búsquedas con muchos filtros).
Nunca borrar el proyecto, la rama principal ni la base de datos desde la consola. Tampoco regenerar la contraseña de la base sin actualizar DATABASE_URL en Vercel y en GCP (Secret Manager) al mismo tiempo; si no, la tienda queda sin conexión.

5. Cloudinary (imágenes)

Consola: https://console.cloudinary.com

Para qué sirve

  • Almacena todas las imágenes de la tienda: fotos de productos, banners del home, imágenes de categorías y del pop-up.
  • Las entrega optimizadas (formato y tamaño adecuados para cada dispositivo) mediante su red de distribución (CDN), lo que acelera la tienda.
  • Cuando el administrador sube una imagen en el panel /admin, la API la envía a Cloudinary con las claves guardadas en las variables de entorno.

Qué pasa si falla

La tienda sigue abierta y se puede comprar, pero las imágenes dejan de verse y no se pueden subir nuevas. Afecta mucho la confianza del cliente y las ventas.

Qué tener en cuenta

  • Plan y límites: Cloudinary mide el uso en créditos (almacenamiento, ancho de banda y transformaciones). Verificar en la consola (Settings / Dashboard) el plan actual y el porcentaje de créditos usados. Si se superan, puede restringir la entrega de imágenes.
  • Fecha de cobro: si el plan es de pago, anotarla aquí: [completar con la fecha que muestre la cuenta]. Si es plan gratuito, no hay cobro pero sí límites mensuales.
  • Claves: la tienda usa tres datos (CLOUD_NAME, API_KEY, API_SECRET) configurados en Vercel y en GCP. Si se regeneran en Cloudinary, hay que actualizarlos en ambos lugares.
  • No borrar imágenes desde la biblioteca de Cloudinary: los productos las referencian por enlace y quedarían con la foto rota.

Qué revisar (mensualmente)

  1. Dashboard: créditos usados, almacenamiento y ancho de banda del mes.
  2. Que el correo de la cuenta reciba y se lean los avisos de cuota (80 % / 100 %).
  3. Abrir la tienda y confirmar que las imágenes cargan.

8. Otros servicios que usa la tienda (referencia)

Además de los cuatro anteriores, la tienda depende de otras cuentas que también conviene tener documentadas: GitHub (código y despliegues), Wompi y Mercado Pago (pagos), Resend (correos de confirmación), Vendelo (envíos), Sentry (monitoreo de errores) y el registrador del dominio. Este manual cubre los cuatro servicios de infraestructura; los demás pueden añadirse en una próxima versión.
